Interrupciones de flanco y serial (DMA + IDLE)

Se parte del proyecto de la clase anterior con un LED que parpadea por interrupción del TIM2 cada 100 ms. Para otro tiempo más largo no hace falta otro timer: un contador dentro de la misma interrupción da 2 segundos. Luego un pulsador con interrupción externa (EXTI) cambia un LED en el instante en que se presiona, y se explican prioridades y subprioridades en el NVIC. Al final se configura el USART con DMA en recepción y la técnica de IDLE line detection con la librería UARTRX, que activa una bandera cuando llega una trama; se prueba en Proteus con COMPIM, Hercules y el terminal serial de VS Code.

Fase 1

Un timer para varias tareas

1.1

La interrupción que ya teníamos

▶ 1:08

El TIM2 genera una interrupción cada 100 ms y en TIM2_IRQHandler (archivo stm32f4xx_it.c) se cambia un LED. Para otro tiempo se podría configurar otro timer, pero los timers son recursos y hay que ahorrarlos.

1.2

Contador como base de tiempo

▶ 3:26

Con la base de 100 ms, 2 segundos son 20 interrupciones. Se declara un contador de 8 bits, se incrementa en cada interrupción y al llegar a 20 se cambia el otro LED y se reinicia. Con más contadores se manejan más tareas con el mismo timer.

/* USER CODE BEGIN PV */
uint8_t contador = 0;
/* USER CODE END PV */

/* USER CODE BEGIN TIM2_IRQn 1 */
contador++;
if (contador > 20)
{
  HAL_GPIO_TogglePin(LED3_GPIO_Port, LED3_Pin);
  contador = 0;
}
/* USER CODE END TIM2_IRQn 1 */

La IA propuso 10 y otro LED. Y si el código queda fuera de un bloque USER CODE, CubeMX lo borra al regenerar.

1.3

Arrancar el timer

▶ 16:06

Si no parpadea nada, revisa que el timer esté arrancado antes del while, una línea por cada timer que uses. Si sale el error de Ninja, F1 > CMake: Delete Cache and Reconfigure.

/* USER CODE BEGIN 2 */
HAL_TIM_Base_Start_IT(&htim2);
/* USER CODE END 2 */
Fase 2

Interrupción por flanco

2.1

El pin como GPIO_EXTI

▶ 19:29

Para atender un pulsador en el mismo instante en que se presiona se usa una interrupción externa por flanco (un flanco es el paso de 0 a 1 o de 1 a 0). En CubeMX haz clic en el pin y elige GPIO_EXTIx (el número depende del pin) en vez de GPIO_Input. Ponle nombre y en GPIO vuelve a ponerle Pull-up, porque se reinicia.

2.2

Habilitar en el NVIC

▶ 21:54

En System Core > NVIC (Nested Vectored Interrupt Controller) aparecen todas las interrupciones. Habilita la EXTI line interrupt de tu pin; la del TIM2 ya estaba.

2.3

Prioridades y subprioridades

▶ 22:29

Con 4 bits hay prioridades de 0 a 15, y 0 es la más alta. Si llega una interrupción más prioritaria, la otra se deja a medias y se atiende la nueva. En Priority Group se puede repartir los 4 bits: por ejemplo 2 bits de prioridad (0 a 3) y 2 de subprioridad, que sirve de desempate entre dos con la misma prioridad.

Aquí el pulsador queda en 0 y el TIM2 en 1. El Time base del sistema queda con la prioridad más baja permitida (3 si usas 2 bits; si queda en 15 sale en rojo).

Este manejo fino de prioridades es lo que permite al STM32 trabajar en tiempo real para control industrial.

2.4

Código en la interrupción

▶ 28:00

Al generar código aparece EXTIx_IRQHandler en stm32f4xx_it.c. Ahí se cambia el LED; no hace falta leer el pin en el main. Con varias interrupciones externas habría que verificar cuál se activó.

/* USER CODE BEGIN EXTI2_IRQn 0 */
HAL_GPIO_TogglePin(LED4_GPIO_Port, LED4_Pin);
/* USER CODE END EXTI2_IRQn 0 */
2.5

Elegir el flanco

▶ 29:05

En la configuración del pin, en GPIO mode eliges el flanco: subida, bajada o ambos. Con pull-up el pin está en 1 y al presionar pasa a 0, así que es flanco de bajada (Falling edge).

2.6

Cómo se reparten los tiempos

▶ 33:33

Mientras el main espera los 500 ms del HAL_Delay, el micro atiende las interrupciones: cada 100 ms la del timer y, en cualquier momento, la del pulsador. Si las dos coinciden, primero la de mayor prioridad y luego vuelve a la otra. Parece que todo pasa al tiempo, pero no.

Fase 3

Recepción serial con DMA e IDLE

3.1

USART con DMA en recepción

▶ 37:04

Para el parcial hay que recibir órdenes por Bluetooth o WiFi. En Connectivity activa el USART en Asynchronous a 9600 (ahora se usan TX y RX). En DMA Settings agrega un DMA para RX en modo Normal: el DMA (Direct Memory Access) guarda los caracteres en memoria sin usar la CPU.

3.2

Interrupción del USART

▶ 40:21

En NVIC Settings del USART marca USART global interrupt. La técnica que se usa es IDLE line detection: el micro detecta la pausa (línea en reposo) al final de una trama y avisa que llegaron los datos.

3.3

Agregar la librería

▶ 42:52

Crea la carpeta librerias y copia uart.c/.h (transmisión), UART_INT_DMA_IDLE.c y UARTRX.c/.h (recepción). En el main incluye uart.h y UARTRX.h junto con las librerías básicas de C, y pulsa el botón del generador de CMake (con FPU por software para simular).

3.4

Funciones __weak

▶ 45:16

En los drivers de la HAL muchas funciones tienen __weak (débil). Si escribes en otro archivo una función con el mismo nombre sin __weak, esa es la que se ejecuta. Así la librería toma el control de la interrupción de recepción sin tocar los archivos de la HAL.

3.5

Configurar el puerto en UARTRX.c

▶ 52:47

En UARTRX.c se declara el huart que usas con extern y una estructura por puerto con el manejador, el USART y el tamaño del búfer: 100 o 200 para Bluetooth o WiFi básico, 256 o más para IoT.

extern UART_HandleTypeDef huart1;
UARTRXS UARTRX1 = {&huart1, USART1, 100};
3.6

Callback y errores

▶ 55:10

En el callback de recepción, por cada UART usado hay un bloque que guarda cuántos datos llegaron y activa una bandera. No se procesa ahí: la interrupción debe ser rápida y el main se encarga. También hay un bloque por puerto para limpiar errores y que no se bloquee si llega basura. Si usas otro puerto (por ejemplo un GPS), se copia el bloque.

3.7

Iniciar y leer en el main

▶ 57:53

Antes del while se inicia la recepción del puerto. En el while, si la bandera está en 1, se procesa la trama y se reinicia el DMA. Para probar, primero se devuelve lo que llega; luego eso se reemplaza por un procedimiento procesa_rx(). Baja el HAL_Delay del while a 100 ms.

/* USER CODE BEGIN 2 */
HAL_TIM_Base_Start_IT(&htim2);
uartRX_It_idle_dma_init(&UARTRX1);
/* USER CODE END 2 */

while (1)
{
  HAL_GPIO_TogglePin(LED_GPIO_Port, LED_Pin);
  HAL_Delay(100);
  if (UARTRX1.flag_rx == 1)
  {
    uartx_write_text(&huart1, UARTRX1.trama_rx); // eco de prueba
    //procesa_rx();
    uartRX_DMA_Re_init(&UARTRX1);
  }
}
Fase 4

Probar en Proteus

4.1

COMPIM y puertos virtuales

▶ 61:24

Crea un par de puertos virtuales con el programa de puertos serie virtuales. En Proteus coloca un COMPIM en uno de ellos a 9600 en ambos lados y conecta TX con TX y RX con RX (el COMPIM no va cruzado; un módulo real sí).

4.2

Eco con Hercules

▶ 65:28

Con la simulación corriendo (los LEDs siguen funcionando) abre el otro puerto en Hercules a 9600. Lo que envías vuelve igual. Si ves números, clic derecho en la zona de recepción y quita el modo HEX.

4.3

Secuencias en el terminal de VS Code

▶ 67:06

El terminal serial de VS Code permite guardar secuencias (nombre y dato, con CR+LF) y enviarlas con un clic, mejor que las tres líneas de Hercules para probar órdenes como encender un motor o un LED.

4.4

Cómo buscar una falla

▶ 71:06

Con el RX del adaptador USB-serial se puede espiar la comunicación: en el pin RX del micro ves si el módulo está enviando; en el TX del micro ves si el micro recibió y respondió. Así se sabe si el problema es del módulo o del programa.

4.5
