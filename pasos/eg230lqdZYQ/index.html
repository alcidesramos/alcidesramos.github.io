Clase 38: OneWire y el sensor DS18B20

El DS18B20 usa el protocolo OneWire: un solo pin que pasa de salida a entrada con tiempos de pocos microsegundos. Las librerías típicas usan HAL_GPIO_Init para cambiar la dirección del pin y son demasiado lentas a baja frecuencia; aquí se cambia la dirección directamente en los registros, para Blue Pill (F1) y para F4/F7/H7.

Fase 1

Proyecto

1.1

Conexión

▶ 1:08

El DS18B20 necesita una resistencia pull-up (4.7k) del pin de datos a positivo. El dato va a un pin cualquiera, aquí PB10. Para ver la temperatura usamos USART1 (PA9) con un cable USB-UART.

1.2

Reloj, UART y pin

▶ 3:26

Con la tarjeta real puedes usar el cristal y la velocidad máxima. Activa USART1 asíncrono a 9600. Pon PB10 como GPIO_Output con la etiqueta one (obligatoria para la librería); la librería cambia el pin entre salida y entrada.

Fase 2

Cómo funciona la librería

2.1

Reset del bus

▶ 7:52

El maestro pone el bus en 0 al menos 480 µs, pasa el pin a entrada, espera 60 µs y lee: si el sensor responde con un 0, está presente.

uint8_t onewire_reset()
{
    uint8_t sen_ok = 0;
    HAL_GPIO_WritePin(onewire_GPIO_Port, onewire_Pin, 0);  // saca un cero
    Output_Pin(onewire_GPIO_Port, onewire_Pin);            // pin como salida
    delay_us(480);                                          // tiempo minimo por datasheet
    Input_Pin(onewire_GPIO_Port, onewire_Pin);             // pin como entrada
    delay_us(60);                                           // espera ver si hay sensor
    if (!(HAL_GPIO_ReadPin(onewire_GPIO_Port, onewire_Pin))) sen_ok = 1;
    else sen_ok = 0;
    delay_us(480);
    return (sen_ok);
}
2.2

Cambiar el pin de dirección rápido

▶ 8:57

Con HAL_GPIO_Init (forma lenta) el cambio de dirección tarda demasiado y se pierde la sincronización a baja velocidad. Por eso puertos.c lo hace por registros: busca el número del pin con un for (GPIO_Pin es un 1 desplazado) y escribe directo en MODER (2 bits por pin en F4), OTYPER (push-pull u open drain), OSPEEDR y PUPDR. En la Blue Pill (F1) usa CRL/CRH con 4 bits por pin.

2.3

Escribir y leer bits

▶ 17:49

Escribir un 0: bus en bajo unos 60 µs. Escribir un 1: bus en bajo unos pocos µs y soltar. Leer: el maestro baja el bus un instante, lo suelta y muestrea antes de 15 µs. Por eso cada microsegundo cuenta.

2.4

Retardo con DWT

▶ 15:33

En delays.h se elige el retardo; con DWT no necesitas calibrar y funciona hasta a baja velocidad. Inicialízalo antes del while.

#define Delay_us delay_us_dwt
Fase 3

Leer la temperatura

3.1

El programa

▶ 16:43
delay_us_dwt_init();
onewire_reset();   // recomendado: el primer dato sale bien
while (1)
{
    temperatura = DS18b20_temp();
    sprintf(texto, "Tempe=%.2f\r\n", temperatura);
    uartx_write_text(&huart1, texto);
    HAL_Delay(800);   // el sensor es lento para convertir
}

Habilita -u _printf_float en MCU Settings para que sprintf muestre el float.

3.2

En la tarjeta real

▶ 19:31

La terminal muestra unos 30 °C y sube al calentar el sensor. Un dato raro suele ser un cable suelto.

Fase 4

Simular en Proteus

4.1

Oscilador interno a 16 MHz

▶ 20:44

Proteus no simula bien el cristal externo: usa HSI en la entrada del PLL y como reloj del sistema, a 16 MHz (lo mínimo que simula bien con esta librería). En la vida real la librería funciona hasta con cristales de 8 MHz en la Blue Pill.

4.2

Simulación funcionando

▶ 21:52

Con el DS18B20 de Proteus y un Virtual Terminal se ve la temperatura y cambia al mover el valor del sensor. Si cambias a las funciones lentas de HAL, la simulación deja de funcionar.

4.3

Pull-up interno (opcional)

▶ 24:08

Sin la resistencia externa no funciona. Puedes activar el pull-up interno en Input_Pin de puertos.c (PUPDR = GPIO_PULLUP), pero se recomienda la resistencia externa: el interno a veces da errores de sincronización.

En Proteus pon la resistencia en modo digital: consume menos recursos y la simulación es más exacta.
