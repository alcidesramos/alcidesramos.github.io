Recibir comandos por el UART

Lección 29 del curso. Con un PIC16F876A, un L293D con un motor, dos leds y el Virtual Terminal de Proteus se reciben órdenes de un solo carácter: letras para prender y apagar leds y números para girar o parar el motor. Se ve el problema de los retardos largos en el programa principal, la versión que se queda esperando el dato y por qué un solo carácter no es la forma más segura de mandar órdenes.

Fase 1

Preparar el proyecto

1.1

El circuito

▶ 0:00

El circuito tiene un PIC16F876A, un L293D que mueve un motor, dos leds y el Virtual Terminal conectado al puerto serial. La idea es mandar órdenes por serial para prender y apagar los leds y cambiar el giro del motor.

1.2

Configuración inicial

▶ 1:45

Proyecto nuevo a 4 MHz. Los puertos quedan como salida y el pin RC7 (RX) como entrada. Se inicia el UART a 9600, un PWM de baja frecuencia para el motor y se manda un HOLA MUNDO para comprobar la transmisión.

TRISB = 0;
TRISC = 0;
TRISC7_bit = 1;   // entrada rx

UART1_Init(9600);
PWM1_Init(300);
PWM1_Set_Duty(127);
PWM1_Start();
UART1_Write_Text("HOLA MUNDO");
1.3

Recepción continua

▶ 5:12

En el registro de recepción hay un bit que habilita la recepción continua. Aunque la librería lo maneja, se deja explícito para recordar que el micro queda listo para recibir varios caracteres seguidos.

CREN_bit = 1;   // habilita la recepcion continua
1.4

Funciones del motor

▶ 6:18

El motor va en RB0 y RB1. Se hacen tres funciones: m1derecha, m1izquierda y m1quieto, que ponen las combinaciones 1-0, 0-1 y 0-0 en esos pines.

Fase 2

Leer y decidir

2.1

Leer si hay dato

▶ 8:42

En el ciclo principal un led parpadea con un retardo corto. Se pregunta con UART1_Data_Ready si llegó algo y, si llegó, se lee con UART1_Read.

while (1)
{
  if (UART1_Data_Ready() == 1)
  {
    dato_rx = UART1_Read();
    // aqui se analiza el dato
  }
  led = ~led;
  Delay_ms(200);
}
2.2

Switch de órdenes

▶ 9:51

Con un switch se decide qué hacer según el carácter: a y b prenden y apagan el led 1, c y d el led 2, y los números 0, 1 y 2 mandan el motor a la derecha, a la izquierda o lo paran.

switch (dato_rx)
{
  case 'a': led1 = 1; break;
  case 'b': led1 = 0; break;
  case 'c': led2 = 1; break;
  case 'd': led2 = 0; break;
  case '0': m1derecha(); break;
  case '1': m1izquierda(); break;
  case '2': m1quieto(); break;
}
2.3

Probar en Proteus

▶ 12:11

Desde el Virtual Terminal se mandan las letras y los números y se ve cómo responden los leds y el motor.

Fase 3

El problema del bloqueo

3.1

Retardos largos

▶ 12:43

Si el programa principal se demora, por ejemplo con un retardo de 5 segundos, las órdenes que lleguen en ese tiempo no se atienden porque el micro no está revisando el puerto.

3.2

Esperar el dato

▶ 13:50

Otra forma es quedarse esperando hasta que llegue un dato. Así no se pierde ninguna orden, pero el programa queda bloqueado: el led del ciclo principal deja de parpadear y solo cambia cuando llega una orden.

while (UART1_Data_Ready() == 0);   // espera un dato
dato_rx = UART1_Read();
3.3

Limitaciones

▶ 16:00

Esta forma sirve si el micro solo va a recibir órdenes y actuar. Un solo carácter es fácil de confundir con ruido, así que en la siguiente lección se usan tramas, y más adelante interrupciones para poder hacer varias cosas a la vez.
