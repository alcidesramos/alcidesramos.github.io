Interrupción de timer, flanco y serial (grupo I)

La clase arranca con la tarea: contar interrupciones del timer para cambiar un LED cada 2 segundos sin usar retardos. Luego se configura un pulsador como interrupción externa por flanco de bajada con pull-up, se explican las prioridades y subprioridades del NVIC y se cambia un LED dentro de su procedimiento. Al final se activa la recepción del USART1 por DMA con detección de línea en reposo, se explica qué significa una función weak en C y se usa la librería UARTRX para devolver por el puerto lo que llega, como prueba de que el micro recibe bien las tramas.

Fase 1

Tarea: contador en la interrupción del timer

1.1

Variable contador

▶ 6:47

El timer interrumpe cada 100 ms. Para cambiar un LED cada 2 s se declara una variable uint8_t (no hace falta una de 32 bits) en la zona de variables privadas del archivo stm32f4xx_it.c, iniciada en cero.

/* USER CODE BEGIN PV */
uint8_t count = 0;
/* USER CODE END PV */
1.2

Contar hasta 20 dentro de la interrupción

▶ 8:27

En TIM1_UP_TIM10_IRQHandler se incrementa el contador y, al llegar a 20 (20 × 100 ms = 2 s), se reinicia y se cambia el LED. Así el main sigue con su propio parpadeo y el timer lleva su cuenta aparte.

count++;
if (count >= 20)
{
  count = 0;
  HAL_GPIO_TogglePin(LED3_GPIO_Port, LED3_Pin);
}

Si el conteo se hiciera en el main con retardos, mientras el micro está en el HAL_Delay no podría detectar otra cosa. Por eso se trabaja con interrupciones.

Fase 2

Interrupción externa por flanco

2.1

Pulsador con pull-up en Proteus

▶ 14:55

Se agrega un pulsador a tierra en el pin PB2. En vez de poner una resistencia externa se usa el pull-up interno del micro, así el pin está en 1 y pasa a 0 al pulsar.

2.2

Modo de interrupción por flanco de bajada

▶ 20:12

En CubeMX el pin se configura como GPIO_EXTI2 y en su configuración se escoge el modo. Hay flanco de subida, de bajada y ambos; como el pulsador va a tierra con pull-up, se escoge flanco de bajada (falling edge).

2.3

Habilitar en el NVIC y prioridades

▶ 22:24

En System Core → NVIC se marca EXTI line2 interrupt. Cada interrupción tiene prioridad de preferencia y subprioridad: un número menor es mayor prioridad (0 es la más alta). Con 4 bits hay 16 niveles, de 0 a 15.

2.4

Grupo de prioridades

▶ 25:49

En Priority Group se reparten los 4 bits entre prioridad y subprioridad. Por ejemplo, con 2 bits para cada una quedan 4 prioridades (0 a 3) y 4 subprioridades. El System tick timer viene en 15 y no conviene tocarlo.

2.5

Código de la interrupción externa

▶ 28:02

Al generar código aparece EXTI2_IRQHandler en stm32f4xx_it.c. Ahí se cambia el LED4 cada vez que se pulsa. La IA puede sugerir el LED equivocado: revisa siempre lo que propone.

/* USER CODE BEGIN EXTI2_IRQn 0 */
HAL_GPIO_TogglePin(LED4_GPIO_Port, LED4_Pin);
/* USER CODE END EXTI2_IRQn 0 */

En la vida real el pulsador tiene rebote y el LED puede cambiar varias veces. Aquí solo se busca entender el concepto.

2.6

Vista Outline en VS Code

▶ 38:45

La vista Outline muestra todos los procedimientos del archivo abierto y permite saltar a cada interrupción sin buscarla a mano.

Fase 3

Recepción serial por DMA con detección IDLE

3.1

Librerías para recibir

▶ 33:55

La librería uart se sigue usando para transmitir. Para recibir se agregan UARTRX y UART_INT_DMA_IDLE. IDLE significa línea en reposo: el micro detecta cuándo dejan de llegar datos, así sabe que llegó la trama completa y no letra por letra.

3.2

Agregar las librerías al proyecto

▶ 39:53

Se copian los archivos en la carpeta de librerías, se usa el botón mágico para agregarlas al CMake (con FPU por software) y se escriben los include necesarios.

3.3

USART1 con DMA en recepción

▶ 43:17

En Connectivity → USART1 se pone modo asíncrono a 9600 baudios, ahora usando TX y RX (PA9 y PA10). En DMA Settings se agrega USART1_RX (de periférico a memoria) para que los datos se guarden solos en un buffer.

3.4

Interrupción del USART en el NVIC

▶ 45:32

En NVIC se habilita la interrupción global del USART1. Ahí se puede cambiar su prioridad respecto al timer y al flanco.

3.5

Qué significa weak

▶ 47:18

Las interrupciones de periféricos como UART y SPI ya no se escriben en stm32f4xx_it.c sino en los drivers HAL. Allí la función HAL_UARTEx_RxEventCallback está declarada como __weak (débil): si en otro archivo .c se escribe la misma función sin weak, el compilador usa la nueva. Así la librería trae su propio callback.

3.6

Configurar el puerto en UARTRX.c

▶ 49:31

Se declara como extern cada UART que se use y se asocia un nombre de la librería (UARTRX1, UARTRX2…, UARTNEXTION, GPS_UARTRX, MQTT_UARTRX) con el puerto real y el tamaño del buffer. Para Bluetooth o WiFi básico 100 datos están bien; para MQTT o GPS hay que subir a 256 o 512.

extern UART_HandleTypeDef huart1;
UARTRXS UARTRX1 = {&huart1, USART1, 100};
3.7

Lo que hace la interrupción

▶ 52:49

Dentro de la interrupción no se procesa nada: solo se guarda cuántos datos llegaron y se activa una bandera. El main revisa la bandera y procesa a su ritmo, sin cargar la interrupción.

3.8

Iniciar la recepción antes del while

▶ 54:23

En el main, debajo del arranque del timer, se inicia la recepción por DMA con detección IDLE para cada puerto que se use. Si hay GPS o Nextion en otro UART, se repite la línea con su nombre.

HAL_TIM_Base_Start_IT(&htim1);
uartRX_it_idle_dma_init(&UARTRX1);

La IA sugirió líneas que no van. Copia solo lo que indica el machete del .h.

3.9

Revisar la bandera en el while

▶ 57:45

En el while se pone un if por cada puerto. Como prueba, el micro devuelve por el mismo puerto la trama que recibió; luego se reinicia el DMA para la siguiente recepción.

if (UARTRX1.flag_rx == 1)
{
  uartx_write_text(&huart1, UARTRX1.trama_rx);
  //procesa_rx();
  uartRX_DMA_Re_init(&UARTRX1);
}
Fase 4

Prueba en Proteus

4.1

COMPIM en Proteus

▶ 59:53

Se agrega el COMPIM y se conectan TX (PA9) y RX (PA10). El COMPIM se conecta directo (TX con TX y RX con RX); los módulos reales casi siempre van cruzados.

4.2

Puertos virtuales

▶ 62:05

Con el programa de puertos seriales virtuales se crea el par COM1 ↔ COM2. El COMPIM usa COM1 y la terminal COM2, ambos a 9600 baudios (físicos y virtuales).

4.3

Eco con Hércules

▶ 63:12

Se abre Hércules en COM2 a 9600 y se envía un mensaje: el micro lo devuelve. En la primera prueba no respondió; se revisaron pines y la configuración del USART en CubeMX, se guardó todo, se regeneró el código y funcionó.

Guarda los archivos en VS Code antes de generar código en CubeMX para evitar conflictos.

4.4

Cómo depurar una comunicación real

▶ 66:43

Con el RX de un programador USB-serial (y tierra común) se puede espiar una línea. Si no llega nada al RX del micro, el problema está afuera (módulo, cableado). Si en el TX del micro salen caracteres raros, los baudios están mal. Si no sale nada, el problema está en el programa del micro.

4.5

Secuencias en la terminal de VS Code

▶ 69:55

La terminal serial de VS Code tiene Sequences: se guardan comandos con nombre y se envían con un clic, sin tener que escribirlos cada vez.

4.6

Procesar la trama y tarea

▶ 73:50

Se crea un procedimiento procesa_rx() donde se compara lo recibido para actuar. Tarea individual simulada: dos comandos, por ejemplo LED1=ON* y LED1=OFF*, para prender y apagar otro LED en Proteus. Investigación: qué es PWM y cómo se implementa en el micro.
