sprintf en el LCD y números flotantes en VS Code

Clase virtual sobre el proyecto del LCD de la clase anterior. Un LCD solo recibe caracteres, así que para mostrar una variable hay que convertirla a cadena con sprintf. Se arma un contador de 0 a 10 y se corrige el problema del dígito que queda pegado dándole ancho al formato; luego se agrega un contador decimal de 0,5 en 0,5. Para que %f funcione hay que habilitar el uso de flotantes en el proyecto con el generador de CMake, eligiendo FPU por software para simular en Proteus. Al final se repasan los protocolos I2C (dos hilos, direcciones de 7 bits, pull-up, velocidades) y SPI (MOSI, MISO, SCK y CS) para que cada grupo sepa explicar los sensores de su proyecto.

Fase 1

Mostrar un contador en el LCD

1.1

Crear la variable

▶ 7:17

Un contador es una variable. Como solo cuenta de 0 a 10, basta un entero sin signo de 8 bits. Se declara en main.c en la zona de variables, inicializada en cero. Deja como comentario lo que había en el while para probar solo esto.

uint8_t contador = 0;
1.2

El LCD no escribe números

▶ 22:12

Si pones Lcd_Text(2, 3, contador); el compilador da error. Al display se le mandan caracteres ASCII, no números; eso de escribir una variable y que salga es cosa de Arduino. En C hay que convertir la variable a cadena con sprintf.

1.3

sprintf y su arreglo de texto

▶ 24:30

El primer parámetro de sprintf es un arreglo de char donde se guarda la cadena; debe ser del tamaño del display o mayor (16 o 20). Luego va el formato entre comillas y después la variable.

La IA propone %d (entero con signo), pero el contador nunca es negativo, así que lo correcto es %u (entero sin signo).

char texto[20];
...
sprintf(texto, "%u", contador);
Lcd_Text(2, 3, texto);
1.4

Incluir las librerías de C

▶ 27:58

Para usar sprintf hay que incluir librerías estándar de C (no hay que copiar archivos, ya vienen con el compilador). Conviene dejar siempre estas cinco en los includes de usuario:

/* USER CODE BEGIN Includes */
#include "stdio.h"
#include "string.h"

#include "stdint.h"
#include "stdlib.h"
#include "math.h"
/* USER CODE END Includes */

stdbool.h solo hace falta si vas a usar true y false.

1.5

Incrementar y reiniciar

▶ 33:18

Incrementa el contador, compáralo con el límite y vuelve a cero. Agrega un retardo para que se vea el conteo.

sprintf(texto, "%u", contador);
Lcd_Text(2, 3, texto);
contador++;
if (contador > 10) contador = 0;
HAL_Delay(500);
1.6

Dar formato: ancho, ceros y texto

▶ 36:56

Al pasar de 10 a 0 queda pegado el 0 del 10, porque el display no se borra. Se arregla con el formato:

  • %2u: ocupa siempre 2 casillas y borra lo anterior.
  • %02u: rellena con ceros a la izquierda (00, 01, 02...).
  • Texto antes y después: "con=%02u V" escribe el texto tal cual y pone el número donde está el %.
sprintf(texto, "con=%02u V", contador);
Fase 2

Contador con decimales

2.1

Variable float y formato %f

▶ 42:12

Para contar de 0,5 en 0,5 hasta 5,5 se usa una variable float. En el formato, %3.1f quiere decir 3 casillas en total (el 5, el punto y el 5) y 1 decimal. Con dos decimales serían 4 casillas: %4.2f.

float contf = 0.5;
...
sprintf(texto, "conf=%3.1f", contf);
Lcd_Text(4, 1, texto);
contf += 0.5;
if (contf > 5.5) contf = 0;

La IA puso un ancho de 2 para un número de 3 caracteres. Revisa siempre lo que sugiere.

2.2

Habilitar los flotantes en el proyecto

▶ 48:55

Por defecto el proyecto no imprime flotantes con sprintf (para ahorrar memoria) y en el LCD sale vacío o en cero. Hay que activarlo en CMake. El botón del generador de CMake (o el script de Python si no lo tienes instalado) trae las opciones: incluir la ruta de las librerías, usar librerías float para sprintf, generar .hex y .bin, optimización de Release y el modo FPU.

2.3

FPU por software para Proteus

▶ 51:50

La Black Pill calcula flotantes por hardware (FPU), que es más rápido, pero Proteus no lo simula. Para simular elige el modo FPU software; en la tarjeta real usa hardware. Pulsa Aceptar / Generar, compila y carga de nuevo el programa en Proteus.

Fase 3

Repaso de I2C y SPI

3.1

I2C

▶ 55:01
  • Bus de dos hilos: SDA (datos) y SCL (reloj).
  • Cada dispositivo tiene una dirección de 7 bits: hasta 128 en el mismo bus, si los cables no son muy largos.
  • Necesita resistencias pull-up a positivo en SDA y SCL, entre 2,2 kΩ y 10 kΩ; lo ideal 4,7 kΩ. Ojo: si varios módulos ya las traen, quedan en paralelo.
  • Velocidades: estándar 100 kbit/s, fast 400 kbit/s y algunos micros 1 Mbit/s.
  • Varios dispositivos pueden ir en el mismo puerto I2C si no repiten dirección. En Proteus la dirección del LCD I2C se ve en sus propiedades.
3.2

Otros displays

▶ 59:36

Los OLED pequeños también son I2C (de uno o dos colores fijos por zona). Los TFT son como pantallas de celular: muestran fotos y colores, pero gastan mucha más memoria y suelen usar SPI. Cada grupo debe investigar el display que use en su proyecto.

3.3

SPI

▶ 60:55

SPI usa MOSI (salida del maestro, entrada del esclavo), MISO (entrada del maestro, salida del esclavo) y SCK (reloj), más un pin de habilitación (CS) por cada esclavo, que se configura como salida GPIO. Tiene más cables que I2C pero es mucho más rápido: con el micro a 84 MHz el SPI puede ir a 42 MHz. Por eso se usa en pantallas y memorias.

3.4

Para la próxima

▶ 64:48

Investigar el ADC (bits, resolución, frecuencia de muestreo y el teorema de Nyquist) y el protocolo UART. Para cada sensor del proyecto hay que saber si es digital, analógico, I2C, UART o SPI y a qué velocidad trabaja.
