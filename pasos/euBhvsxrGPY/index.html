Interrupción de timer, flanco y serial (grupo H)

Es la misma clase del grupo I con otra configuración del pulsador. Primero se resuelve la tarea: un segundo LED que cambia cada 2 s contando interrupciones del timer de 100 ms. Luego el pulsador va a positivo, con pull-down interno y flanco de subida, en el pin PB6, que cae en la interrupción EXTI9_5; se le da más prioridad que al timer y se explican las subprioridades. Al final se activa el USART1 con DMA en recepción y detección de línea en reposo, se explica la palabra weak y se usa la librería UARTRX para devolver por el puerto lo que llega.

Fase 1

Tarea: contador en la interrupción del timer

1.1

Otro LED con el mismo timer

▶ 0:02

Se agrega otro LED en CubeMX y en Proteus. No hace falta otro timer: no conviene gastar un recurso porque sí.

1.2

Contar hasta 20

▶ 1:23

En la interrupción del TIM1 se incrementa el contador, se compara con 20 (20 × 100 ms = 2 s), se cambia el LED y se reinicia el contador. La IA sugiere valores y LEDs: hay que revisarlos, el que dirige el código es uno.

Contador++;
if (Contador >= 20)
{
  Contador = 0;
  HAL_GPIO_TogglePin(LED2_GPIO_Port, LED2_Pin);
}

Con otro contador y otro valor se pueden tener varias tareas de tiempo con un solo timer.

Fase 2

Interrupción externa por flanco

2.1

¿Dónde poner el pulsador?

▶ 4:22

En el main hay un retardo de 500 ms y en el timer se perderían hasta 100 ms. Para reaccionar de inmediato se usa la interrupción de flanco: el instante en que la señal pasa de 0 a 1 (subida) o de 1 a 0 (bajada).

2.2

Pulsador a positivo en Proteus

▶ 8:14

El pulsador se conecta a positivo en un pin libre y se agrega otro LED. La resistencia no se pone afuera: se usa la interna del micro.

2.3

Pin como interrupción y pull-down

▶ 11:54

El pin se configura como GPIO_EXTI6. En System Core → GPIO se escoge pull-down: si el pulsador va a positivo, la resistencia debe ir a tierra (si fuera a tierra, sería pull-up).

2.4

Flanco de subida

▶ 14:50

Sin pulsar el pin está en 0 y al pulsar sube a 1, así que se escoge External Interrupt Mode with Rising edge trigger detection. También existen el de bajada y el de ambos flancos. Conviene aprender estos términos en inglés técnico.

2.5

Prioridades en el NVIC

▶ 17:03

NVIC es el controlador del vector de interrupciones anidado. Con 4 bits las prioridades van de 0 a 15, y 0 es la más alta. El pin 6 cae en EXTI line[9:5] interrupts. Como el pulsador debe atenderse primero, se le baja la prioridad al timer (el 0 ya es el máximo).

2.6

Subprioridades

▶ 19:50

En Priority Group se parten los 4 bits, por ejemplo 2 bits para prioridad (0 a 3) y 2 para subprioridad. La subprioridad desempata interrupciones con la misma prioridad. Si alguna tenía 15, hay que bajarla al nuevo máximo.

2.7

Código de la interrupción

▶ 21:32

Al generar código aparece EXTI9_5_IRQHandler en stm32f4xx_it.c. Ahí se cambia el LED del pulsador.

/* USER CODE BEGIN EXTI9_5_IRQn 0 */
HAL_GPIO_TogglePin(LED4_GPIO_Port, LED4_Pin);
/* USER CODE END EXTI9_5_IRQn 0 */

Con un pulsador real hay rebote; se puede agregar un antirrebote de 15 a 20 ms. Aquí solo se busca el concepto.

Fase 3

Recepción serial por DMA con detección IDLE

3.1

Detección de línea en reposo

▶ 23:42

La interrupción de recepción serial permite dar órdenes al sistema mientras hace otras cosas. Los datos llegan letra por letra; con IDLE line detection el micro detecta cuando la línea queda quieta y sabe que llegó la trama completa. Se combina con DMA, que guarda los datos directo en memoria.

3.2

USART1 a 9600 baudios

▶ 25:55

En Connectivity → USART1 se pone modo asíncrono y 9600 baudios. Quedan TX en PA9 y RX en PA10; ahora se usan los dos.

3.3

DMA de recepción e interrupción

▶ 27:02

En DMA Settings se agrega USART1_RX y en NVIC Settings se habilita la interrupción del USART. Su prioridad se cambia en System Core → NVIC si hace falta.

3.4

Agregar las librerías

▶ 28:44

Se copian uart, UARTRX y UART_INT_DMA_IDLE a la carpeta de librerías, se usa el botón mágico (FPU por software mientras se simula) y se incluyen uart.h y UARTRX.h en el main. UART_INT_DMA_IDLE solo tiene .c, porque trae el procedimiento de interrupción.

3.5

Qué significa weak

▶ 33:49

En los drivers HAL del UART el callback de recepción está declarado __weak (débil). Si en otro .c se escribe la misma función sin weak, el compilador usa esa. Así la interrupción queda en la librería y no hay que buscarla en los drivers.

3.6

Asociar el puerto en UARTRX.c

▶ 36:01

Se declara extern cada huart que se use y se asocia un nombre de la librería con el puerto real y el tamaño del buffer. El nombre puede ser UARTRX1, UARTRX2… o los de Nextion, GPS o MQTT; lo que debe coincidir con CubeMX es el puerto. 100 datos bastan para la mayoría; MQTT o GPS necesitan más.

extern UART_HandleTypeDef huart1;
UARTRXS UARTRX1 = {&huart1, USART1, 100};
3.7

La interrupción solo avisa

▶ 38:46

En la interrupción, por cada puerto, solo se guarda cuántos datos llegaron y se activa una bandera. También hay un manejo de errores por puerto. El procesamiento se hace en el main para no demorar la interrupción.

3.8

Iniciar y revisar la bandera

▶ 39:53

Antes del while se inicia la recepción, como se hizo con el timer. En el while, si la bandera está activa, como prueba se devuelve la trama por el mismo puerto y luego se reinicia el DMA para detectar la siguiente.

uartRX_it_idle_dma_init(&UARTRX1);

while (1)
{
  HAL_GPIO_TogglePin(LED_GPIO_Port, LED_Pin);
  HAL_Delay(200);
  if (UARTRX1.flag_rx == 1)
  {
    uartx_write_text(&huart1, UARTRX1.trama_rx);
    //procesa_rx();
    uartRX_DMA_Re_init(&UARTRX1);
  }
}

El eco es solo para probar que llegan los datos. Al final se desactiva y se procesa la trama.

Fase 4

Prueba en Proteus

4.1

COMPIM y puertos virtuales

▶ 45:33

Se agrega el COMPIM con terminales TX y RX en PA9 y PA10. En Proteus va directo (TX con TX); los módulos reales casi siempre van cruzados. Con el programa de puertos virtuales se crea el par COM1 ↔ COM2, y en el COMPIM se pone COM1 con los dos baudios (físico y virtual) en 9600.

4.2

Eco con Hércules

▶ 49:47

En Hércules, pestaña Serial (no TCP), se abre COM2 a 9600 y se envía un texto: el micro lo devuelve.

4.3

Secuencias en VS Code

▶ 51:33

Hércules solo tiene tres casillas de envío. La terminal serial de VS Code tiene Sequences: se guardan varios comandos con nombre y se envían con un clic. Hay que cerrar Hércules antes, porque dos programas no pueden abrir el mismo puerto.

4.4

Tarea y detección de fallas

▶ 55:33

Se crea un procedimiento procesa_rx() para analizar lo recibido. Tarea: enviar dos comandos, como LED1=ON* y LED1=OFF*, para prender y apagar otro LED en Proteus. Para encontrar fallas en un montaje real se conecta el RX de un programador (con tierra común) al RX del micro: si no llega nada, falla el módulo; en el TX del micro, si no sale nada falla el programa y si salen caracteres raros, los baudios.
