Retardos y debugger en MikroC

Lección 13 del curso. Con un contador de 0 a 9 en un display se muestra que Delay_ms y Delay_us solo aceptan constantes y que para un retardo variable se usa Vdelay_ms. Luego se crea el procedimiento delay_seg con un parámetro y una variable local para hacer retardos en segundos, y se usa el debugger de MikroC para medir cuánto tarda y para ver variables. Al final se ven las mismas variables en Proteus cargando el archivo .cof.

Fase 1

Retardos de MikroC

1.1

Contador de 0 a 9

▶ 0:00

Se crea el proyecto retardos en la carpeta Clase 13 (PIC16F877A a 4 MHz) y se copian de la clase anterior el #define del display y el vector de códigos. Un for muestra los números de 0 a 9.

#define display PORTD
const char codigos[] = {63, 6, 91, 79, 102, 109, 125, 7, 127, 111};
char cuenta;

void main() {
  TRISD = 0;
  while (1) {
    for (cuenta = 0; cuenta < 10; cuenta++) {
      display = codigos[cuenta];
      Delay_ms(100);
    }
  }
}
1.2

Delay_ms y Delay_us solo aceptan constantes

▶ 3:22

Delay_ms(1) es lo mismo que Delay_us(1000), pero a los dos solo se les puede pasar un número fijo. Si se escribe una variable, el compilador da error.

1.3

Vdelay_ms para retardos variables

▶ 4:27

Para un retardo que dependa de una variable está Vdelay_ms (solo en milisegundos). Con Vdelay_ms(cuenta * 50) el conteo arranca rápido y se va haciendo más lento.

Vdelay_ms(cuenta * 50);
Fase 2

Retardo propio en segundos

2.1

Procedimiento con parámetro

▶ 5:34

Por primera vez un procedimiento recibe un valor: entre los paréntesis se declara la variable (unsigned int time). Al llamarlo, por ejemplo delay_seg(3), ese valor se carga en time.

2.2

Variables locales

▶ 6:39

Una variable declarada como parámetro o dentro de un procedimiento es local: solo existe dentro de él. Si se intenta usar en el main, el compilador dice que no está declarada.

2.3

El retardo con un for

▶ 7:43

El procedimiento repite un retardo de un segundo tantas veces como diga time. Luego se usa en el contador para que cambie cada segundo.

void delay_seg(unsigned int time) {
  char cont;
  for (cont = 1; cont <= time; cont++)
    Delay_ms(1000);
}

...
display = codigos[cuenta];
delay_seg(1);
Fase 3

Depurar

3.1

Activar la barra del debugger

▶ 9:59

En View > Toolbars se activa la Debugger Toolbar. Con Start Debugger el programa corre dentro de MikroC y se puede avanzar línea por línea.

3.2

Medir cuánto tarda un código

▶ 11:09

Se llama delay_seg(1) antes del while a propósito, se inicia el debugger, se pone en cero el cronómetro del Watch Clock y se pasa por encima con Step Over. Marcó 1000,02 ms: el retardo está bien. Si se necesitara más precisión se ajustaría el valor, por ejemplo a 999.

3.3

Ver variables

▶ 12:15

En Watch Values se agregan variables, como cuenta o el vector codigos, y se ve cómo cambian al avanzar. Con clic derecho sobre el valor se escoge si se muestra en decimal, hexadecimal o binario, con o sin signo.

3.4

Ver variables en Proteus con el .cof

▶ 13:22

En Project > Edit Project (u Output Settings) se activa Generate COF file y se compila. En Proteus se carga el .cof en vez del .hex, se arranca en pausa y en Debug > Watch Window se arrastra la variable. Con clic derecho se cambia su formato.

El archivo de Proteus debe estar en la misma carpeta que el proyecto de MikroC.

Para ver variables en Proteus hay que cargar el archivo .cof; con el .hex no aparecen.

3.5

Step Into o Step Over

▶ 16:12

Step Into entra a los procedimientos propios para ver qué hacen por dentro. En las funciones de MikroC, como Delay_ms, conviene usar Step Over, porque si no se termina dentro de código en ensamblador. El debugger sirve para encontrar errores y para medir tiempos.
